## 2. FFI (Foreign Function Interface) Architecture

CFFI provides a mechanism to interact with C libraries from Python. Unlike standard Python `ctypes`, which relies purely on dynamic assembly and manual struct alignment definitions in Python, CFFI operates at both the C API and ABI levels.

```
+-------------------------------------------------------------------------------+
|                             Python Application Layer                          |
|                 (e.g., curl_cffi easy/multi/session interfaces)               |
+-------------------------------------------------------------------------------+
                                        |
                   +--------------------+--------------------+
                   |                                         |
                   v                                         v
+-------------------------------------+   +-------------------------------------+
|        cffi.FFI (api.py)            |   |    _cffi_backend.FFI (C Engine)     |
|   - cdef() C-declaration parser     |   |   - Low-level libffi call bridges   |
|   - typecache & lock management     |   |   - def_extern() C callback router  |
|   - set_source() code generator     |   |   - newp(), cast(), string()        |
+-------------------------------------+   +-------------------------------------+
                   |                                         |
                   v                                         v
+-------------------------------------------------------------------------------+
|                    Compiled C Extension Module (_wrapper.pyd)                 |
|               - Generated by out-of-line API mode recompiler                  |
|               - Direct compile-time linkage to libcurl symbols                |
+-------------------------------------------------------------------------------+
                                        |
                                        v
+-------------------------------------------------------------------------------+
|                          Native Target Shared Library                         |
|                      (libcurl-impersonate / BoringSSL)                        |
+-------------------------------------------------------------------------------+
```

### 2.1 The `FFI` Class (`cffi/api.py:16-797`)
The top-level interface of CFFI is the `FFI` class:
- **Initialization (`cffi/api.py:34-93`)**:
  - Selects the backend (`import _cffi_backend as backend`).
  - Initializes the declaration parser `self._parser = cparser.Parser()` (`cffi/api.py:61`).
  - Initializes concurrency locks `self._lock = allocate_lock()` (`cffi/api.py:60`).
  - Binds core type singletons: `self.BVoidP`, `self.BCharA`, `FFI.NULL = self.cast(self.BVoidP, 0)`, `FFI.CData`, `FFI.CType`, and `self.buffer = backend.buffer` (`cffi/api.py:80-92`).

### 2.2 Modes of Operation

CFFI supports four distinct modes across two design axes: **ABI vs. API** mode, and **In-line vs. Out-of-line** mode.

#### 1. ABI Mode vs. API Mode
- **ABI Mode (Binary Level)**:
  - Invoked via `ffi.dlopen("libname.so")` (`cffi/api.py:130-146`).
  - Does not require a C compiler at build or runtime.
  - Dynamically binds functions and types by calling untyped dynamic symbols via `libffi`.
  - Drawback: Struct layouts, integer enum values, and macros must be declared with exact byte alignments manually; differences in host C compiler struct padding can lead to segmentation faults.
- **API Mode (Source/C-Compiler Level)**:
  - Invoked via `ffi.set_source("module_name", c_header_source)` (`cffi/api.py:630-642`) and `ffi.compile()` (`cffi/api.py:705-723`).
  - Uses the host C compiler to compile an intermediate C file generated by CFFI (`cffi/recompiler.py`).
  - The C compiler verifies structure offsets, integer widths, bitfields, and macro expansions directly against system headers.
  - Generates type-safe wrapper functions that eliminate dynamic call-overhead.

#### 2. In-line vs. Out-of-line
- **In-line Mode**:
  - The `ffi.cdef()` and `ffi.verify()` calls execute dynamically every time the Python script or module is imported.
  - Requires `pycparser` and (in API mode) a C compiler at runtime.
- **Out-of-line Mode (Ahead-Of-Time / AOT)**:
  - A build script (e.g., `build.py` or `setup.py`) runs `ffi.set_source()` and `ffi.compile()`.
  - Generates a standalone C extension module (`<name>.pyd` on Windows, `<name>.so` on Linux/macOS).
  - At runtime, the application imports the compiled module directly (`from ._wrapper import ffi, lib`).
  - **No C compiler or `pycparser` is invoked during normal runtime execution**. The runtime relies solely on `_cffi_backend` and the compiled extension.

### 2.3 Core API Primitives

| Method | Source Citation | Functional Contract |
| :--- | :--- | :--- |
| `ffi.cdef(csource)` | `cffi/api.py:94-105` | Parses C declarations (types, function prototypes, structs) using `pycparser`. |
| `ffi.new(cdecl, init)` | `cffi/api.py:237-260` | Allocates a C object managed by Python GC. The allocated memory is freed when the wrapper `CData` instance is garbage collected. |
| `ffi.cast(cdecl, source)` | `cffi/api.py:286-293` | Casts between C types (e.g., integer to pointer, `void*` to struct pointer). |
| `ffi.string(cdata, maxlen)` | `cffi/api.py:295-311` | Decodes a null-terminated C string (`char*`) to Python `bytes`. |
| `ffi.buffer(cdata, size)` | `cffi/api.py:92` (`_cffi_backend.buffer`) | Returns a zero-copy Python buffer referencing raw C memory. |
| `ffi.from_buffer(cdecl, py_buf)` | `cffi/api.py:343-360` | Exposes a Python bytearray or buffer as a `CData` pointer without copying memory. |
| `ffi.memmove(dest, src, n)` | `cffi/api.py:361-375` | Wraps C `memmove()` to copy `n` bytes between C pointers and Python buffers. |
| `ffi.new_handle(x)` | `cffi/api.py:533-535` | Creates an opaque `void*` handle encapsulating a Python object reference (`borrowed`). |
| `ffi.from_handle(x)` | `cffi/api.py:536-538` | Recovers the original Python object from an opaque `void*` handle across C boundaries. |
| `ffi.def_extern(onerror)` | `cffi/api.py:774` / `_cffi_backend.FFI` | Decorator used in out-of-line API mode to define Python functions callable as C callbacks. |

### 3.2 Compilation & Runtime Import Mechanism
`curl-cffi` is built using CFFI's **Out-of-line API mode**:
1. At build time, `curl-cffi` compiles a C extension named `curl_cffi._wrapper` (`_wrapper.pyd` on Windows, `_wrapper.so` on Linux).
2. At runtime, `curl_cffi` imports `_cffi_backend` and the compiled extension:
   ```python
   # curl_cffi/__init__.py:63-68
   import _cffi_backend  # noqa: F401  # required by _wrapper

   from .__version__ import __curl_version__, __description__, __title__, __version__  # noqa: F401

   # This line includes _wrapper.so into the wheel
   from ._wrapper import ffi, lib
   ```
3. Runtime object types:
   - `curl_cffi._wrapper.ffi` is an instance of `<class '_cffi_backend.FFI'>`.
   - `curl_cffi._wrapper.lib` is an instance of `<class '_cffi_backend.Lib'>` exposing all compiled libcurl C functions directly.

#### 3. Callback Implementation via `@ffi.def_extern()`
`libcurl` relies on C function pointer callbacks for writing chunks, reading upload streams, seeking, debug tracing, and socket polling. `curl-cffi` implements all of these using `@ffi.def_extern()`:

- **Error-Trap Wrapper (`curl_cffi/curl.py:94-106`)**:
  ```python
  def _store_callback_error(return_value: int):
      def onerror(exc_type, exc_value, traceback):
          if traceback is not None:
              # CFFI cannot propagate exceptions through C, but exposes the callback
              # arguments through this frame so the owning handle can retain it.
              callback_args = traceback.tb_frame.f_locals
              userdata = callback_args.get("userdata", callback_args.get("clientp"))
              if userdata is not None:
                  context = ffi.from_handle(userdata)
                  context.exception = exc_value
          return return_value

      return onerror
  ```
- **Registered Callbacks**:
  - `debug_function` (`curl.py:110-120`): `@ffi.def_extern(onerror=_store_callback_error(0))`
  - `buffer_callback` (`curl.py:162-169`): `@ffi.def_extern(onerror=_store_callback_error(CURL_WRITEFUNC_ERROR))`
  - `write_callback` (`curl.py:177-190`): `@ffi.def_extern(onerror=_store_callback_error(CURL_WRITEFUNC_ERROR))`
  - `read_buffer_callback` (`curl.py:192-212`): `@ffi.def_extern(onerror=_store_callback_error(CURL_READFUNC_ABORT))`
  - `read_callback` (`curl.py:214-234`): `@ffi.def_extern(onerror=_store_callback_error(CURL_READFUNC_ABORT))`
  - `seek_buffer_callback` (`curl.py:236-245`): `@ffi.def_extern(onerror=_store_callback_error(CURL_SEEKFUNC_FAIL))`
  - `timer_function` (`aio.py:117-139`): `@ffi.def_extern()` for `CURLMOPT_TIMERFUNCTION`
  - `socket_function` (`aio.py:141-169`): `@ffi.def_extern()` for `CURLMOPT_SOCKETFUNCTION`

#### 4. Opaque Handle Contexts (`new_handle` / `from_handle`)
When passing Python state into C callbacks (e.g., upload file objects or write buffers), `curl-cffi` encapsulates them in `ffi.new_handle()`:
```python

elif option == CurlOpt.WRITEDATA:
    c_value = ffi.new_handle(_CallbackContext(value))
    self._write_handle = c_value
    lib._curl_easy_setopt(
        self._curl, CurlOpt.WRITEFUNCTION, lib.buffer_callback
```

Inside the C callback, the Python object is unpacked safely:
```python

```

#### 5. High-Speed Memory Transfers
- Receiving network chunks without intermediate Python string allocation (`curl_cffi/curl.py:167`):
  `ffi.buffer(ptr, nmemb)[:]`
- Copying memory into C buffers during upload streaming (`curl_cffi/curl.py:210, 232`):
  `ffi.memmove(ptr, data, len(data))`

### 4.3 Packaging & Deployment Implications for Android
1. **The Installation Failure Mode**:
   When installing `curl-cffi` on Android (e.g., inside Termux or an Android app build using Flet/BeeWare):
   - Package managers find the matching `curl_cffi-0.16.3-cp314-cp314-android_24_arm64_v8a.whl`.
   - The installer attempts to satisfy `curl-cffi`'s declared dependency `cffi>=2.0.0`.
   - Because no Android wheel for `cffi` exists on PyPI, the installer falls back to compiling from source (`cffi-2.1.1.tar.gz`, `uv.lock:34`).
2. **Compilation Requirements on Android**:
   Compiling `cffi-2.1.1.tar.gz` from source fails unless the following native build dependencies are present on the build system:
   - Android NDK (Clang toolchain targeting `aarch64-linux-android` API 24+).
   - Python 3.14 C development headers (`Python.h`).
   - `libffi` headers (`ffi.h`) and precompiled static/shared library `libffi.so` cross-compiled for Android.
   - Host `pycparser` package.
3. **Recommended Solutions for Android Environments**:
   - **Termux**: Install the pre-compiled package from the Termux repository:
     ```bash
     pkg install python-cffi
     ```
   - **Chaquopy / BeeWare / Kivy (p4a)**: Use the vendor-provided wheel mirror or recipe (e.g., Chaquopy distributes pre-built `cffi` wheels in its Maven repository).
   - **Custom App Build Pipelines (Flet/Flutter Android)**:
     Cross-compile `cffi` using `cibuildwheel` and Android NDK ahead of time, hosting the resulting `cffi-2.1.1-cp314-cp314-android_24_arm64_v8a.whl` in a local or private package index.
